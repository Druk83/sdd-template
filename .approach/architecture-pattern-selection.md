# Architecture Pattern Selection — выбор архитектурного паттерна

Адаптер (`adapter`) для выбора архитектурного паттерна из внешнего каталога
[arch-patterns](https://github.com/Druk83/arch-patterns).

## Назначение

Адаптер связывает внешний каталог архитектурных паттернов с этапами разработки
технической документации. Он не копирует каталог в репозиторий и не выбирает
паттерн без подтверждённых драйверов проекта.

## Область применения

- этап `[2]` — сравнение и выбор архитектурного паттерна;
- этап `[7]` — применение выбранного паттерна при системном проектировании;
- этап `[8]` — проверка соответствия структуры ПО принятому решению.

## Входы

Перед выбором прочитай:

1. результаты этапа `[1]`;
2. требования и NFR, если они уже существуют;
3. разделы `3.1` и `3.2` документа `.requirements/обоснование выбора.md`;
4. `.approach/registry.json`;
5. доступную версию внешнего каталога `arch-patterns`.

Если внешний каталог недоступен, не выбирай паттерн по памяти. Зафиксируй
GAP с причиной недоступности и останови выбор до получения источника или
подтверждённого решения разработчика.

## Правила классификации

Перед сравнением отдели архитектурный паттерн от других типов подходов:

| Вид | Примеры из реестра | Роль в выборе |
|---|---|---|
| Архитектурный паттерн | `Layered`, `Hexagonal`, `Clean Architecture`, если присутствуют в источнике | Организация границ и зависимостей приложения |
| Паттерн потоков данных | `CQRS` | Разделение чтения и записи |
| Паттерн хранения событий | `Event Sourcing` | Фиксация изменений и восстановление состояния |
| Интеграционный паттерн | `Pub/Sub`, `Context Map` | Взаимодействие контекстов и компонентов |
| Паттерн проектирования кода | `Repository`, `Factory`, `Strategy` | Реализация отдельных компонентов |
| Нотация | `ArchiMate` | Представление архитектуры, а не организация приложения |

Перечень кандидатов архитектурного паттерна бери из доступного источника и
не расширяй его неподтверждёнными вариантами.

## Процедура выбора

1. Извлеки архитектурные драйверы из требований, NFR, масштаба, доменной
   сложности, ограничений команды, интеграций и требований к развёртыванию.
2. Зафиксируй факты и ссылки на документы проекта для каждого драйвера.
3. Составь минимум два кандидата, если источник и факты проекта это позволяют.
4. Для каждого кандидата оцени соответствие драйверам, ограничения,
   стоимость усложнения, риски и влияние на этапы `[7]` и `[8]`.
5. Отдельно зафиксируй причины отказа от рассмотренных альтернатив.
6. Выбери один архитектурный паттерн или зафиксируй, что выбор невозможен
   без решения разработчика.
7. Запроси подтверждение кандидатов и итогового выбора по процедуре
   `.manifest/sddmanifest.md`.
8. После подтверждения запиши решение в H8-документ
   `docs/requirements/обоснование выбора.md`.

## Обязательная карточка решения

В разделе `3.5.4` и итоговом разделе `3.5.6` должны быть указаны:

| Поле | Содержание |
|---|---|
| `pattern_name` | Название выбранного архитектурного паттерна из источника |
| `pattern_kind` | `architecture-pattern` |
| `source_url` | URL внешнего каталога |
| `source_revision` | Commit, tag или другая воспроизводимая версия |
| `retrieved_at` | Дата обращения к источнику |
| `drivers` | Драйверы, повлиявшие на выбор |
| `evidence_refs` | Ссылки на требования, NFR и предыдущие результаты |
| `candidates` | Рассмотренные варианты |
| `rejected_alternatives` | Отклонённые варианты и причины отказа |
| `decision` | Выбранный вариант или статус нерешённого выбора |
| `approval` | Кто и когда подтвердил решение |
| `downstream_impact` | Влияние на `[7]`, `[8]` и связанные документы |

## Правила продолжения работы

- До подтверждения выбор является кандидатом, а не архитектурным решением.
- При изменении драйверов карточка решения пересматривается.
- Изменение выбранного паттерна требует оценки влияния на архитектуру,
  структуру ПО, данные и уже созданные документы.
- Если внешний источник изменился, существующее решение не переписывается
  автоматически: создаётся новая версия решения с новой `source_revision`.

## Критерии готовности

- [ ] Источник и его воспроизводимая версия зафиксированы.
- [ ] Архитектурный паттерн отделён от паттернов данных, интеграции и кода.
- [ ] Драйверы подтверждены ссылками на документы проекта.
- [ ] Рассмотренные и отклонённые альтернативы описаны.
- [ ] Решение подтверждено разработчиком или оформлено как GAP.
- [ ] Влияние на этапы `[7]` и `[8]` зафиксировано.
