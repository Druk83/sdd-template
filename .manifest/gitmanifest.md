# Git Manifest (H2)

Политики и обязательные стандарты проверки коммита и публикации релиза в репозитории Framework и проектах-потребителях.

---

## git.H3.1 Разделяй готовность к коммиту, проверку коммита и публикацию
Не объявляй релиз опубликованным по локальным файлам или сообщению о выполненной команде. Применяй этот протокол при подготовке релизного коммита, при сообщении разработчика «готов сделать коммит» для релиза и при продолжении его публикации. Для обычного коммита применяй проверку состава и индекса без релизных артефактов.
**Почему важно:** каждый переход подтверждает отдельный факт; пропуск проверки оставляет незавершённые данные в истории и может породить повторный коммит.

---

## git.H4.1 Подтверди состояние «готов к коммиту» после проверки индекса
**Входные данные:** целевая версия проекта, базовая ветка, один выбранный способ публикации (прямая отправка или запрос на включение изменений — pull request, PR), ожидаемый список файлов и утверждённая тема одного коммита.
**Что делать:**
1. Определи текущие `HEAD`, ветку, состояние рабочей директории и индекса через `git status`, `git diff` и `git diff --cached`. Уточни актуальность удалённой базовой ветки; если проверить её нельзя, сообщи об ограничении до следующего шага. Проверь существующие ветки и PR, если они доступны.
2. Для релиза сверь относящиеся к нему задачу и issues, CHANGELOG, README, дату, статус, версии в проектных каталогах и манифестах, документацию и проверки, требуемые проектом. Удали из публикуемого состояния незаполненные даты и признаки кандидата (`draft`, `planned`, `in-progress`, «кандидат релиза»). Не переписывай исторические упоминания и независимые незавершённые задачи; объясни исключения.
3. Проверь полный рабочий diff командой `git diff`, список неотслеживаемых и изменённых файлов через `git status` и ошибки форматирования командой `git diff --check`. Сопоставь фактический состав с ожидаемым и устрани блокеры до команды коммита.
4. Предложи разработчику одну проверенную команду `git add` для согласованных путей и запроси результат. После её выполнения повторно проверь `git status`, `git diff --cached --name-status`, полный `git diff --cached` и `git diff --cached --check`. Сверь индекс с ожидаемым составом, включая отсутствие лишних файлов и пропущенных изменений. Если индекс изменился позже, повтори проверку.
5. Только после проверки индекса сообщи «готов к коммиту», точную тему одного коммита и одну команду `git commit`; запроси полный SHA или вывод `git show -s` после выполнения разработчиком.
**Запрещено:** считать предварительную проверку рабочего дерева подтверждением состава будущего коммита; выполнять `git add` или `git commit` за разработчика согласно H1.3.

---

## git.H4.2 Подтверди состояние «коммит проверен» по объекту Git
**Входные данные:** полный SHA, сообщённый разработчиком, утверждённая тема и сохранённый ожидаемый состав коммита.
**Что делать:** проверь объект через `git rev-parse --verify <SHA>^{commit}` и `git show -s --format=%H%n%P%n%s <SHA>`. Сверь полный SHA, число и значения родителей, тему, состав через `git diff-tree --root --no-commit-id --name-status -r <SHA>` и содержимое через `git show --format=fuller --find-renames <SHA>` с подготовленным набором. Если ветка или индекс изменились, определи фактическое состояние до дальнейших команд.
**Переход:** только после совпадения этих данных сообщи «коммит проверен» и готовь публикацию. Неверный, сокращённый или несуществующий SHA не заменяй догадкой; запроси корректный вывод.

---

## git.H4.3 Подтверди состояние «релиз опубликован» по удалённой ветке
**Входные данные:** проверенный SHA, выбранный способ публикации, базовая ветка и фактический результат отправки или слияния, выполненных разработчиком.
**Что делать:** получи актуальный SHA удалённой основной ветки через `git ls-remote --heads origin <base>` и её дерево через `git fetch origin <base>`. Проверь, что удалённая ветка содержит проверенный SHA либо фактический коммит интеграции PR; сверь опубликованные версию, дату и статус через `git show FETCH_HEAD:<path>`. Для релиза Framework дополнительно проверь через `git ls-remote --tags origin <tag>`, что удалённый tag указывает на проверенный коммит. При работе через PR проверь его базу, состояние и отсутствие дубля. Сверь локальную ветку и рабочую директорию через `git status`; расхождения назови явно.
**Переход:** сообщай «релиз опубликован» только при подтверждённом удалённом состоянии. Если доступ к удалённой ветке или PR отсутствует, сообщи «публикация не подтверждена» и запроси проверяемый результат ручной проверки.

---

## git.H3.2 Сохраняй один согласованный путь публикации
Не смешивай прямую отправку, PR и переписывание истории в одной цепочке команд. Каждая следующая команда зависит от проверенного результата предыдущей.
**Почему важно:** удалённое состояние может измениться после любой команды, а продолжение прежнего плана создаёт дубли и риск потери опубликованного релиза.

---

## git.H4.4 Проверяй публикационный путь перед командой
До публикации проверь наличие нужного инструмента и доступа, актуальное состояние удалённой ветки и существующих PR. Предлагай только выбранный путь и одну команду следующего шага; разработчик выполняет `push` и слияние согласно H1.3. Если `gh` или другой CLI отсутствует, не предлагай его установку как обязательный шаг: дай ручной путь через доступный интерфейс и назови непроверяемые факты. При ошибке команды остановись, получи её вывод, заново проверь состояние и лишь затем предложи исправленный шаг. Не создавай второй PR для того же релиза. Переписывание опубликованной истории допускай только после отдельного осознанного решения разработчика и проверки резервной точки; `reset --hard` и `push --force` не являются штатным завершением релиза.

---

## git.H4.5 Сообщай разработчику проверяемый следующий шаг
На каждом переходе назови найденные блокеры, исправленные файлы, проверенные факты, одну команду для разработчика и результат, который нужен для следующей проверки. Не выдавай оставшиеся команды цепочки как применимые после ошибки или неподтверждённого шага.

---

## git.H3.3 Не требуй самоссылку коммита в публикуемом дереве
SHA зависит от содержимого коммита; запись его собственного SHA в это содержимое изменяет SHA. Сохраняй возможность одного релизного коммита.
**Почему важно:** обязательная самоссылка создаёт бесконечную замену SHA или лишний «публикационный» коммит.

---

## git.H4.6 Фиксируй ссылку на коммит после его появления
До коммита укажи в задаче завершённый статус работы и, если секция `## Выполнение (PR/commit)` обязательна, отметь ожидающую внешней фиксации ссылку. После создания коммита помести полный SHA или ссылку в PR, журнал публикации или другую внешнюю запись. Отдельный последующий коммит с этой ссылкой допускается только как явное решение проекта; не обещай одновременно один коммит и SHA этого коммита внутри него. Применяй `task.H4.4`, `pdd.H4.6` и H1.3. Правила `version.H3.4` и `version.H4.9` относятся к версии самого Framework; версию репозитория-потребителя определяй по его документации.
