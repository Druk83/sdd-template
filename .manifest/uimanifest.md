# Манифест документации пользовательского интерфейса (UI Documentation Manifest) (H2)

Манифест определяет порядок планирования пользовательского интерфейса, состав
технических артефактов и правила безопасной работы с эталонными макетами.

## Источник паттернов пользовательского интерфейса (UI-паттернов)

Канонический внешний источник:

`https://github.com/Druk83/ui-patterns.git`

Framework использует только опубликованную ревизию (revision), зафиксированную в
данных происхождения (provenance) UI-пакета. Локальная копия (checkout) не является
входом проектной процедуры и
не указывается в задачах, инструкциях или результатах агента.

## Применимость

Перед созданием UI-артефактов агент определяет, есть ли в требованиях, сценариях,
маршрутах или других источниках пользовательский интерфейс.

- При наличии UI запускается подэтап `[5.a]` после сценариев и до структуры данных.
- Если UI не описан, агент сообщает о пробеле и предлагает добавить UI-контур,
  уточнить тип интерфейса или подтвердить отсутствие UI.
- До решения используется статус `gap`.
- После явного подтверждения отсутствия UI используется `not_applicable`, и подэтап
  не блокирует независимые части SDD.

## Порядок подэтапа `[5.a]`

1. Прочитать `docs/requirements/` и ссылки на источники (source refs), определить
   UI-контур.
2. Получить внешний каталог по официальному URL и закреплённой ревизии (pinned
   revision).
3. Сформировать пул экранов (screen pool) из требований, сценариев, маршрутов, ролей
   и эталонных артефактов (reference artifacts).
4. Предложить для каждого экрана `screen_type`, назначение (purpose), маршрут (route),
   роли, границы, кандидатов паттернов (pattern candidates) и состояния.
5. Получить подтверждение пула экранов.
6. Сформировать матрицу областей просмотра (viewport matrix) в CSS px по
   подтверждённым источникам и получить
   её подтверждение.
7. Выбрать паттерн (pattern) и переиспользуемый шаблон экранного интерфейса (reusable
   screen UI template), сохранив отклонённые варианты (rejected candidates).
8. Создать спецификацию экрана (screen specification) и трассируемость (traceability)
   до требований, сценариев и критериев приёмки.
9. Создать интерактивный эталонный прототип (live reference prototype) только после
   подтверждения спецификации.
10. Выполнить проверки схемы, выполнения, области просмотра, доступности, визуальной
    регрессии и трассируемости.

## Артефакты по умолчанию

Для проекта с UI по умолчанию создаётся полный UI-пакет:

```text
docs/requirements/пользовательский-интерфейс/
├── README.md
├── манифест-спецификации-интерфейса.json
├── пул-экранов.json
├── screens/
│   └── <screen-id>.md
└── references/
    └── <reference-set>/
        ├── screen-manifest.json
        └── <viewport-orientation>/
            ├── index.html
            ├── reference-manifest.json
            ├── README.md
            ├── <screen-artifact>.html
            └── assets/
```

Спецификация экрана и интерактивный эталонный прототип являются разными артефактами.
Прототип имеет статус `reference-only` и не является рабочим интерфейсом продукта
(production UI).

## Контракт пула экранов (screen pool)

Минимальная запись экрана содержит `screen_id`, `title`, `screen_type`, `purpose`,
`route` или `entry_point`, `user_roles`, `user_task`, `pattern_candidates`, `states`,
основные `transitions`, `viewport_candidates`, `source_refs` и `status`.

Допустимые операции разработчика до подтверждения: `add`, `remove`, `merge`, `split`,
`rename`, изменение type, route, role, границ, priority и viewport.

Статусы: `proposed`, `confirmed`, `rejected`, `gap`, `superseded`, `not_applicable`.
Утверждённый пул не изменяется автоматически. Изменение требований создаёт отчёт о
влиянии (impact report) и новую ревизию.

## Контракт области просмотра (viewport)

Область просмотра описывается в CSS px. Физическое устройство указывается только как
`reference_target` и не заменяет CSS viewport.

Размеры берутся в следующем порядке: явные требования, существующие эталонные
артефакты, целевая платформа (target platform) и ограничения продукта, устройство,
явно указанное разработчиком. При отсутствии данных создаётся `gap`; подбор по памяти
агента или названию устройства запрещён.

Для каждого экрана предлагаются применимые профили `portrait`, `landscape`,
`compact`, `narrow`, `wide` и `overflow/stress case`. Для каждой записи фиксируются
width, height, units, orientation, responsive profile, breakpoint/change conditions,
назначение, source, rationale и status.

## Контракт интерактивного эталонного прототипа (live reference prototype)

Прототип использует канонический независимый от фреймворка (framework-neutral)
`HTML/CSS/JS`, запускается автономно (offline) с тестовыми данными (fixture data) и
не использует программный интерфейс проекта (project API), секреты (secrets) или
рабочие данные продукта (production data). Он содержит компоновку (layout), действия,
состояния, переходы, пути обработки ошибок и восстановления, варианты области
просмотра и ориентации, эталонный манифест и артефакты визуальной проверки.

Общий каркас (generic skeleton) хранится во внешнем `ui-patterns`; Framework создаёт
адаптацию под проект (project-specific adaptation) после подтверждения пула экранов,
матрицы областей просмотра и спецификации экрана. Рабочий код продукта (production
code) создаётся только отдельным явно подтверждённым этапом.

## Контрольные точки подтверждения (approval gates)

Обязательные контрольные точки: пул экранов, типы экранов и кандидаты паттернов,
матрица областей просмотра, спецификация экрана, интерактивный эталонный прототип и
переход к реализации продукта (production implementation).

При отклонении варианта сохраняются причина, решение разработчика, дата и ревизия.

## Унаследованные материалы (legacy) и миграция

Существующие `docs/.figma` и другие эталонные каталоги не удаляются и не
переименовываются автоматически. Перед миграцией выполняются инвентаризация
(inventory) и сравнение изменений (diff). Перенос сохраняет HTML, CSS, шрифты
(`fonts`), снимки экрана (`screenshots`), ресурсы (`assets`), манифесты (`manifests`)
и неизвестные пользовательские файлы. Конфликты не перезаписываются автоматически,
создаётся отчёт миграции (migration report), а очистка исходника выполняется
отдельным подтверждаемым действием.
