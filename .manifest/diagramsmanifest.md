# Diagrams Manifest (H2)

Политики и обязательные стандарты создания, именования и хранения диаграмм в документации.

**Инструмент построения изображений:** `.tools/plantuml-render/` для PlantUML, BPMN и DOT/Graphviz (см. README инструмента).

Диаграмма выбирается по смыслу документа, а не по удобству генерации:

- Модель и нотация бизнес-процессов (Business Process Model and Notation, BPMN) — для описания участников, действий, событий и условий перехода.
- PlantUML — для унифицированного языка моделирования (Unified Modeling Language, UML), ArchiMate и других технических диаграмм, для которых уже определена соответствующая модель.
- DOT/Graphviz — для графа нормативного порядка и конечного автомата; этот режим применяется только по правилам `.manifest/normativeordermanifest.md`.

---

## diagrams.H3.1 Храни код диаграммы отдельно от документа
Код диаграммы сохраняется в отдельный файл, не inline в markdown.
**Почему важно:**
Отдельные файлы позволяют версионировать, рендерить и переиспользовать диаграммы.

---

## diagrams.H4.1 Размещай диаграммы в папках diagrams/
```
docs/requirements/
  diagrams/                           # общие диаграммы
    domain-overview.plantuml
    domain-overview.png
  сценарии/
    <domain>/
      diagrams/                       # диаграммы домена
        UC-01-sequence.plantuml
        UC-01-sequence.png
        <process>.bpmn
        <process>.png
        <process>-normative-order.dot
        <process>-normative-order.png
  архитектура/
    diagrams/                         # архитектурные диаграммы
      BL.plantuml
      AL.plantuml
      TL.plantuml
```

---

## diagrams.H3.2 Используй единые конвенции именования
Имена файлов диаграмм следуют строгому формату по типу.
**Почему важно:**
Единообразие упрощает навигацию и автоматизацию.

---

## diagrams.H4.2 Называй файлы по типу диаграммы
| Тип диаграммы | Формат имени | Пример |
|---------------|--------------|--------|
| Обзор домена | `<domain>-overview.plantuml` | `domain-overview.plantuml` |
| Диаграмма последовательности (sequence diagram, UC) | `UC-<NN>-sequence.plantuml` | `UC-01-sequence.plantuml` |
| Диаграмма деятельности (activity diagram, UC) | `UC-<NN>-activity.plantuml` | `UC-01-activity.plantuml` |
| Карта контекстов (Context Map) | `context-map.plantuml` | `context-map.plantuml` |
| ArchiMate слой | `<layer>.plantuml` | `BL.plantuml`, `AL.plantuml` |
| Диаграмма «сущность—связь» (Entity–Relationship Diagram, ERD) | `erd-<domain>.plantuml` | `erd-users.plantuml` |
| BPMN бизнес-процесс | `<process>.bpmn` | `<process>.bpmn` |
| Граф нормативного порядка | `<process>-normative-order.dot` | `<process>-normative-order.dot` |

Для построения ArchiMate-слоев используй эталонные исходники фреймворка:

- `.diagrams/example BL.plantuml`;
- `.diagrams/example AL.plantuml`;
- `.diagrams/example TL.plantuml`.

Эталонные файлы обязательны для изучения перед созданием BL, AL и TL. Они
определяют стиль оформления, но не являются источником сущностей конкретного
проекта. Их названия, идентификаторы и связи нельзя копировать без подтверждения
в документации проекта.

## diagrams.H3.3 Строй BPMN для бизнес-процесса
BPMN используй как графическую модель подтверждённого бизнес-процесса с участниками, действиями, событиями и условиями. Она не заменяет карту процесса, каталог событий
или sequence-диаграмму.

**Почему важно:**
Диаграмма не должна добавлять неподтверждённые шаги и смешивать процесс с другими видами моделей.

---

## diagrams.H4.3 Строй BPMN по подтверждённой модели
**Что делать:**
- Используй пулы (pool) для самостоятельных участников, дорожки (lane) — для ролей, ограниченных контекстов (bounded contexts) или внешних систем внутри участника.
- Показывай явные события начала/окончания (start/end events), задачи (tasks) с глагольными названиями и шлюзы (gateways) для условий и развилок.
- Используй потоки последовательности (sequence flow) внутри участника и потоки сообщений (message flow) между участниками.
- Показывай ошибки и исключения только при подтверждении источником.
- Не добавляй шаги, события, роли и переходы вне подтверждённой карты процесса.
- Описывай один процесс или согласованную область (scope) на одной диаграмме.

**Результат:** `<process>.bpmn` и PNG или SVG рядом с ним, а также ссылка из
соответствующего документа.

---

## diagrams.H3.4 Строй граф нормативного порядка только по запросу
Граф нормативного порядка — конечный автомат переходов между событиями по подтверждённой фактической последовательности. Он не заменяет BPMN.

**Почему важно:**
Без явного запроса и подтверждённых данных граф создаёт ложное ощущение нормативности процесса.

---

## diagrams.H4.4 Создавай нормативный граф только при подтверждённых данных
**Условия:**
- Разработчик явно запросил анализ нормативного порядка.
- Фактическая последовательность событий подтверждена.
- Каноническая модель, текстовая формула, DOT и PNG строятся по одним данным согласно `.manifest/normativeordermanifest.md`.

**Результат:** `<process>-normative-order.dot`, PNG рядом с исходником, текстовая формула и ссылка из документа. При недостатке данных зафиксируй GAP и граф не создавай.

---

## diagrams.H3.5 Рендерь диаграммы через инструмент проекта
Используй `.tools/plantuml-render/` для рендеринга.
**Почему важно:**
Единый инструмент обеспечивает консистентность и не требует локальных зависимостей.

---

## diagrams.H4.5 Запускай рендеринг командой
```bash
# Все диаграммы в docs/requirements/
.tools/plantuml-render/plantuml-render --path docs/requirements/

# Конкретная директория
.tools/plantuml-render/plantuml-render --path docs/requirements/архитектура/diagrams/

# Проверка без рендеринга
.tools/plantuml-render/plantuml-render --dry-run --path docs/requirements/

# Граф нормативного порядка в DOT
.tools/plantuml-render/plantuml-render --diagram-type graphviz \
  --path docs/requirements/сценарии/<domain>/diagrams/<process>-normative-order.dot
```

**Полная документация:** `.tools/plantuml-render/README.md`

---

## diagrams.H3.6 Вставляй ссылку на диаграмму в документ
После рендеринга добавь изображение в markdown с комментарием на исходник.
**Почему важно:**
Документ без ссылки на изображение не покажет диаграмму.

---

## diagrams.H4.6 Вставляй изображение по шаблону
```markdown
### 12.1 Диаграмма событий

<!-- Исходный код: diagrams/domain-events.plantuml -->
![Диаграмма событий домена](diagrams/domain-events.png)
```

**Правила:**
- Комментарий с путем к исходному коду обязателен
- Альтернативный текст (alt text) должен быть описательным.
- Путь относительный от текущего документа

---

## diagrams.H3.7 Проверяй синтаксис перед коммитом
Диаграмма с ошибками синтаксиса не отрендерится.
**Почему важно:**
Битые диаграммы ломают документацию.

---

## diagrams.H4.7 Проверь по списку проверки (checklist) перед коммитом
- [ ] Исходный код сохранён в `*.plantuml`, `*.bpmn` или `*.dot` в папке `diagrams/`
- [ ] Имя файла соответствует конвенции (diagrams.H4.2)
- [ ] Выполнен рендеринг: `.tools/plantuml-render/plantuml-render --path <dir>`
- [ ] PNG создан рядом с исходником
- [ ] В markdown добавлена ссылка на PNG (diagrams.H4.6)
- [ ] Диаграмма отображается корректно

---

**Запрещено:**
- Встроенные (inline) диаграммы в Markdown (` ```plantuml ... ``` `)
- Диаграммы без исходного кода (только PNG)
- Диаграммы в корне документации (используй папку `diagrams/`)
- Рендеринг через внешние сервисы минуя инструмент проекта
- Создание графа нормативного порядка без явного запроса разработчика
- Использование BPMN для архитектурных слоёв, Context Map или детализации вызовов компонентов
