# Gap Resolution Manifest (H2)

Политики и обязательные стандарты классификации, уточнения и закрытия пробелов (GAP).

**Аудитория:** проект-потребитель SDD Framework; **Экспорт:** включён

---

## gapresolution.H3.1 Классифицируй GAP по уровню уточнения
Перед созданием записи в `gap-tracking` определи тип GAP. Тип GAP не равен критичности (HIGH/MEDIUM/LOW) и используется для выбора корректного поведения.

**Если тип = IMPLEMENTATION, GAP не создается.** Такой вопрос решается в текущем или следующем этапе без фиксации в gap-tracking.

---

## gapresolution.H4.1 Типы GAP и алгоритм классификации
| Тип GAP | Признак | Пример | Действие |
|---------|---------|--------|----------|
| CRITICAL | Архитектурная дилемма или противоречие в источниках | SPA vs веб-приложение; IndexedDB vs MongoDB | Создать GAP, запросить решение с вариантами и последствиями |
| CLARIFICATION | Нужна конкретизация из контекста для следующего этапа | Глобальные или per-lap поля сессии | Создать GAP, спросить кратко с контекстом |
| OPTIONAL | Ответ есть в .source/, но требуется подтверждение MUST/SHOULD/COULD | Быстрый комментарий в MVP | Создать GAP, уточнить приоритет |
| IMPLEMENTATION | Вопрос реализации, ответ будет ясен на следующем этапе | Как рендерить диаграммы | Не создавать GAP, решить на этапе |

**Алгоритм классификации:**
1. Есть явный ответ в `.source/` → не создавать GAP, использовать в документе.
2. Ответ выводится логически из этапов [1]-[N] → не создавать GAP, использовать в документе.
3. Вопрос относится к реализации и решается на следующем этапе → тип IMPLEMENTATION, GAP не создавать.
4. Есть противоречие или архитектурная дилемма → тип CRITICAL, создать GAP.
5. Нужна конкретизация для продолжения этапа → тип CLARIFICATION, создать GAP.
6. Нужна только валидация MUST/SHOULD/COULD → тип OPTIONAL, создать GAP.

**Важно:** для созданного GAP критичность заполняется по `gap.H4.2` (HIGH/MEDIUM/LOW) в `.manifest/gapmanifest.md`.

## gapresolution.H3.2 Обогащай контекст перед вопросом
Перед созданием GAP собери проверяемый контекст из исходников и уже принятых
артефактов. Не спрашивай факт, который явно указан или однозначно выводится.
Так вопрос будет содержать только действительно неразрешённую неопределённость.

## gapresolution.H4.2 Выполни предварительную проверку контекста (context preflight)
Для каждого кандидата на GAP:

1. Найди прямые и синонимичные упоминания в `.source/`.
2. Проверь предыдущие этапы и карту зависимостей из трека разработки.
3. Раздели результат на факт, логический вывод, коллизию и выбор.
4. Если остаётся выбор или коллизия, сформируй контекстный буфер GAP.

Если ответ однозначен, GAP не создавай. Если данных недостаточно для вывода,
зафиксируй только то, что не подтверждено источниками.

---

## gapresolution.H3.3 Используй единый формат вопроса GAP
Каждый вопрос к разработчику оформляй одинаково, чтобы было видно основание,
тип решения и дальнейшее действие.

## gapresolution.H4.3 Формат GAP в чате
```markdown
**GAP-NNN: <краткое название>**

Тип: CRITICAL | CLARIFICATION | OPTIONAL
Критичность: HIGH | MEDIUM | LOW

**Контекст вопроса:**
- Источники: <проверенные источники>
- Уже известно: <факты и выводы>
- Не определено: <только остаточная неопределённость>
- Влияние: <затронутые этапы и документы>

**Вопрос:**
<выбор или описание коллизии>

**После ответа:**
<артефакты и документы, которые нужно обновить>
```

Историю предыдущих попыток уточнения добавляй отдельным пунктом только при её
наличии. Тип GAP и критичность не смешивай.

---

## gapresolution.H3.4 Пересчитывай зависимости после решения GAP
Решение GAP считается обработанным только после проверки всех артефактов,
которые используют изменённое понятие, идентификатор, требование или решение.

## gapresolution.H4.4 Пересчитай зависимости после решения (post-resolution recalculation)
После получения решения:

1. Зафиксируй изменённые термины, идентификаторы и утверждения.
2. Найди их в `.source/`, результатах завершённых этапов и связанных диаграммах.
3. Сопоставь найденные ссылки с картой зависимостей трека.
4. Обнови каждый затронутый H8-артефакт или объясни, почему он не меняется.
5. Повтори поиск до отсутствия устаревших ссылок.
6. В отчёте укажи список проверенных документов и остаточные GAP.

Во время SDD этот рецепт является частью манифеста/трека; задачу в `.tasks/`
создавай только для последующей разработки кода.

---

## gapresolution.H3.5 Проверяй H8-результат перед закрытием этапа
Очистка (cleanup) и структурная проверка применяются к результатам в `docs/`, а не к
шаблонам `.requirements/`, где placeholder-маркеры являются частью процедуры.
Это предотвращает ошибочное удаление допустимых маркеров из шаблонов.

## gapresolution.H4.5 Финальная проверка результата
Перед статусом `CLOSED` проверь:

- отсутствие `TODO`, `FIXME`, `XXX` и незавершённых `@update-after`;
- отсутствие незаполненных заполнителей (placeholder), не являющихся частью допустимой разметки;
- наличие обязательных секций и таблиц выбранного манифеста;
- согласованность GAP, требований, ссылок и связанных артефактов.

При ошибке этап не закрывай: исправь результат или создай GAP с описанием
причины, если исправление зависит от решения разработчика.
