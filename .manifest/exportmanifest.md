# Export Manifest (H2)

Стандарт формирования переносимого релиза SDD Framework для проектов-потребителей.
Определяет состав пакета, источник версии, расположение результата и безопасные
границы операций сборщика.

---

## export.H3.1 Идентичность релиза

Релиз имеет следующие неизменяемые идентификаторы:

- отображаемое имя: `SDD Framework`;
- `package_id`: `sdd-template`;
- каталог: `.agents/sdd-template-X.Y.Z`, где `X.Y.Z` — версия SemVer.

В репозитории разработки `.agents/` и `tmp/` используются только для локальной
проверки сборщика и не являются публикуемыми исходными данными. Они исключаются
из Git. В проекте-потребителе агент получает чистые исходники по `ref` из реестра,
запускает `install_framework.py` с корнем исходной копии и `--target-root`,
указывающим корень проекта-потребителя. Установщик создаёт готовый пакет
непосредственно в его `.agents/`; корень исходной копии в проект не переносится.

## export.H3.2 Источник версии

Единственным источником выбора релизов является `release-registry.json` из
репозитория `Druk83/sdd-template.git`. Для `init` и `update` используется его
`default_version`; для `use` — точная запись запрошенной версии. Главный `README.md`
выбранного источника используется только для проверки совпадения версии.

Минимальная поддерживаемая версия — `1.9.0`. Версии ниже `1.9.0` не адаптированы к
сборщику и отклоняются до начала сборки. Для установки, обновления и возврата
разрешён диапазон от выбранной текущей версии до `1.9.0` включительно.

Имя папки используется для быстрого определения установленной версии. Версия в
имени папки, `README.md` релиза и `release-manifest.json` обязаны совпадать.
При несовпадении сборка или установка останавливается.

Рекурсивный поиск релизов, чтение вложенных README для первичного выбора версии и
поиск по исходному коду запрещены.

## export.H3.3 Разрешённый состав

В релизную папку входят:

- `README.md` релиза;
- `sdd-template.instructions.md`;
- `.project-structure.json` проекта-потребителя;
- `.chatlog/.gitkeep` без истории сессий;
- `.manifest/`;
- `.requirements/`;
- `.approach/`;
- `.diagrams/` только с эталонными исходниками диаграмм Framework;
- переносимые инструменты из `.tools/`;
- `release-registry.json` — снимок официального перечня поддерживаемых релизов;
- `.gitignore` пакета для локальных и автоматически создаваемых файлов;
- `release-manifest.json`.

В состав переносимых `.tools/` входят только рабочие файлы инструментов и их README.
Обязательный `agent-logic` переносится полностью вместе с кодом, wrappers,
manifest и инструкциями. Его автоматически создаваемые `.runtime/`, кэш,
локальные настройки и тесты в пакет не входят.

Инструкция `sdd-template.instructions.md` является точкой входа для коротких команд
`инициализируй сдд`, `обнови сдд` и `вернись на версию X.Y.Z`. Эти команды относятся
только к подтверждённому `package_id: sdd-template` и источнику
`Druk83/sdd-template.git`.

## export.H3.4 Запрещённый состав

В пакет не входят:

- `AGENTS.md` мета-репозитория;
- `.tasks/`;
- `.issues/`;
- `.source/`;
- тесты сборщика;
- исходные материалы мета-репозитория, кроме разрешённых эталонных исходников
  диаграмм в `.diagrams/`;
- `.git/`, кэши, runtime, локальные настройки и секреты;
- системные и репозиторные временные данные;
- пользовательский `AGENTS.md` проекта-потребителя.

## export.H3.5 Расположение и границы записи

Сборщик получает два разных корня: `--root` указывает на чистую копию исходного
репозитория в `tmp/`, а `--target-root` — на корень проекта-потребителя. Результат
создаётся только в `<target-root>/.agents/sdd-template-X.Y.Z/`. При установке
промежуточная сборка размещается во вложенном `tmp/` клона и удаляется вместе с ним.
Исходная копия в `tmp/` не переносится в корень проекта.
Для одного запуска создаётся только один клон. Предварительный обзорный каталог
не используется, а имя клона содержит первые 8 символов его фактического commit.

Существующий релиз нельзя перезаписывать молча. При наличии старого релиза сборщик
останавливается и сообщает, какое действие необходимо подтвердить пользователю:
удаление или перенос старого релиза в `tmp/sdd-template-old-X.Y.Z/`.

## export.H3.6 Метаданные релиза

`release-manifest.json` содержит:

- `schema_version`;
- `package_id`;
- `version`;
- `release_dir`;
- `source_repo`;
- `source_commit`;
- `source_dirty`;
- `export_profile`;
- список файлов с размером и SHA-256;
- ссылки на `README.md` и `sdd-template.instructions.md`.

`release-registry.json` в пакете является снимком реестра исходного репозитория.
Для выбора новой доступной версии агент сначала сверяет реестр с источником
`Druk83/sdd-template.git`, а затем использует commit или tag из соответствующей записи.
Для записи с `ref_type: tag` поле `commit` может быть `null`: точный разрешённый
commit фиксируется в `release-manifest.json` после клонирования тега. Для записи
с `ref_type: commit` поля `ref` и `commit` обязательны и должны совпадать.

## export.H3.7 Первичная подготовка проекта-потребителя

Состав релизного пакета не включает рабочие каталоги проекта `.source/`, `.tasks/`
и `.issues/`. После проверки релиза установщик создаёт только отсутствующие элементы
их стандартного каркаса:

```text
.source/README.md
.tasks/README.md
.tasks/done/
.tasks/pdd/@todoregistry.md
.issues/README.md
.issues/done/
docs/requirements/
```

Существующие каталоги и файлы не перезаписываются. В существующий `.gitignore`
добавляются только отсутствующие правила в управляемом блоке; пользовательские
строки сохраняются. Корневой `.chatlog/` проекта не создаётся: журналами Framework
управляет `.agents/sdd-template-X.Y.Z/.chatlog/`.

`docs/requirements/` является рабочим каталогом проекта-потребителя и не входит
в состав релиза. Если он существует, установщик не копирует, не переносит и не
перезаписывает его содержимое. При отсутствии создаются только каталог и
`.gitkeep`.

Файл manifest не включает сам себя в список контрольных сумм. Порядок файлов и ключей
стабилизирован для воспроизводимой проверки.

## export.H3.8 Правила `AGENTS.md`

Файл `AGENTS.md` мета-репозитория не переносится как отдельный файл релиза.
Вместо этого установщик добавляет полный канонический текст инструкций Framework
в управляемый раздел корневого `AGENTS.md` проекта-потребителя. Если корневого
файла нет, установщик создаёт его; если файл существует, добавляется только
управляемый раздел между маркерами:

```text
<!-- SDD Framework: managed section begin -->
...
<!-- SDD Framework: managed section end -->
```

Пользовательские инструкции вне управляемого раздела сохраняются полностью.
При одной корректной паре маркеров управляемый раздел заменяется актуальным
каноническим текстом Framework. При конфликте маркеров или явного правила
проекта установщик не перезаписывает спорное содержимое, а возвращает список
`agents.conflicts` для решения пользователем. Отсутствие файла не блокирует
установку.

## export.H3.9 Проверки готового пакета

До публикации сборщик обязан проверить:

- соответствие имени папки версии из корневого README;
- наличие обязательных файлов;
- отсутствие запрещённых путей;
- корректность `release-manifest.json`;
- контрольные суммы всех файлов пакета, кроме manifest;
- отсутствие второй папки SDD Framework в `.agents/`.

## export.H3.10 Очистка временных данных

Временные данные проекта-потребителя создаются только в одном каталоге клона
в корневом `tmp/`. Промежуточная сборка находится во вложенном `tmp/` этого
клона. Сборщик
или агент не удаляет весь `tmp/` и не удаляет чужие каталоги. После проверки
установщик возвращает `status: installed_pending_cleanup` и
`cleanup.status: awaiting_user_confirmation`; агент обязан показать пользователю
`cleanup.question`, дождаться ответа и завершить очистку отдельным вызовом с
`--cleanup-action delete` или `--cleanup-action keep`. Удалять разрешено только
созданный клон и его вложенный staging.
