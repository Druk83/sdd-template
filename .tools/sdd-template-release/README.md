# sdd-template-release — сборка релиза SDD Framework

> Версия инструмента: `0.2.2`.

Инструмент собирает и устанавливает переносимый релиз SDD Framework из чистых исходников
репозитория `Druk83/sdd-template.git`. Папки `.agents/` и `tmp/` в корне
репозитория разработки являются только локальными dev-артефактами и исключены
из Git.

Сборка отклоняет файлы через символические и жёсткие ссылки (hard links) в
исходном дереве. Установщик также отклоняет такие файлы и пути назначения под
target root до записи.
Чтение, копирование, создание и удаление выполняются через проверенные открытые
каталоги из `.tools/fs_boundary.py`; соединения каталогов Windows (junction),
другие точки повторной обработки (reparse points) и вложенные точки монтирования
POSIX отклоняются. При переносе старого релиза Windows использует каталог назначения,
переданный открытым дескриптором; POSIX использует эксклюзивное переименование
относительно дескрипторов каталогов. Если безопасная операция недоступна на
файловой системе, действие завершается ошибкой без запасного перехода на
непроверенный путь.

Проверены Windows (Python 3.14) и Linux (Python 3.11): обычные файлы,
символические ссылки, Windows junction и управляемая подмена пути. Вариант
`renameatx_np` для macOS предусмотрен, но на macOS пока не испытан. Открытый
дескриптор POSIX удерживает исходный объект при подмене его имени, однако процесс
с правом записи в родительский каталог может перенести сам уже открытый каталог.
Для такой недоверенной одновременной записи нужна изоляция прав на рабочее дерево.

В проекте-потребителе `framework.release_dir` задаёт единственную активную
версию. Symlink и junction не создаются. Текстовые пути разрешаются через
`FRAMEWORK_ROOT`; доказанные кликабельные ссылки на старую версию установщик
мигрирует по проверенному плану. Если процесс прервётся, активный пакет
определяется по `framework.release_dir` после проверки manifest и SHA-256.
Исторические ссылки сохраняются.
Архивная локальная Markdown-ссылка блокирует перенос или удаление пакета,
на который указывает. Если её цель уже отсутствует, post-install проверка
возвращает `missing`. Для освобождения старого пакета ссылку следует отдельно
перевести на проверенный immutable ref; массовая миграция архивов не выполняется.
Для возврата к версии до 1.9.6 применяйте установщик 1.9.6 или новее к
проверенному source clone целевой версии. Он переносит адрес на старый пакет;
установщик из старого source clone не управляет этим адресом. Перед переносом
или удалением прежнего пакета inventory сверяется повторно.

## Install/update procedure

Используй этот раздел только по явному запросу на установку или обновление.
Получай release-registry.json из официального репозитория
Druk83/sdd-template (raw-файл ветки main). Для init/update выбери default_version,
для use — запрошенную версию; возьми соответствующую запись ref и install_path.
Не выбирай версию поиском по CHANGELOG и не клонируй main как пакет Framework.

Создай уникальную папку sdd-template-update-<32 hex> в системном temp. Получи
source clone только по ref из реестра с глубиной 1. Для tag используй именно tag;
для commit — fetch этого commit и detached checkout. Проверь, что HEAD равен
выбранному commit (для tag зафиксируй разрешённый commit), прочитай версию и
переименуй каталог клона в sdd-template-source-X.Y.Z-<первые 8 знаков HEAD>.
Клон должен находиться непосредственно в папке workspace.

Запусти из source clone один раз:

    python <source-root>/.tools/sdd-template-release/install_framework.py --source-root <source-root> --target-root <project-root> --action <init|update|use> --write

Для use добавь --version X.Y.Z. Не запускай предварительный dry-run и не проси
подтверждение, если проверка не выявила коллизию. Установщик сам проверяет
происхождение, manifest, SHA-256, границы записи, пользовательские данные и ссылки.
При конфликте он остановится до спорного изменения и сообщит конкретное решение.
После успешной операции он удалит только проверенный клон и пустой workspace.
Он не удаляет весь системный temp или временные данные проекта.

Установщик, boundary helpers и тесты остаются в source repository и не копируются
в проект-потребитель. Повседневная работа с документацией не использует этот
раздел.

## Быстрый старт

Проверить состояние без записи:

```text
python .tools/sdd-template-release/build_release.py
```

Для промежуточного непубликуемого кандидата проверь сборку командой:

```text
python .tools/sdd-template-release/verify_release.py --candidate
```

Проверка создаёт пакет во временной директории и проверяет `release-manifest.json`, состав и
SHA-256 всех файлов, копию `release-registry.json` и обязательные файлы поставляемого пакета.
Рабочие `.agents/` и `tmp/` мета-репозитория не изменяются. Успешный результат этой команды
является обязательной локальной проверкой кандидата.

Если следующий commit предназначен для публикации релиза, перед ним переведи запись
реестра из `candidate` в `supported`, установи `default_version` на новую версию,
укажи фактическую дату публикации в CHANGELOG.md и `released_at`, затем проверь пакет
без флага `--candidate`:

```text
python .tools/sdd-template-release/verify_release.py
```

После commit и создания tag проверь опубликованный релиз:

```text
python .tools/sdd-template-release/verify_release.py --published
```

Общий протокол готовности коммита, проверки полного SHA и подтверждения удалённой
публикации задан в [gitmanifest.md](../../.manifest/gitmanifest.md). Проверка
`--published` подтверждает локальный ref и состав пакета; после отправки разработчиком
отдельно сверь удалённую основную ветку и tag по `git.H4.3`.

Проверка требует, чтобы все записи со статусом `supported` ссылались на существующие
immutable refs, а текущий commit совпадал с ref текущей версии. Для публикации новой версии
создай tag локально на проверенном commit, выполни проверку, а затем используй atomic push
ветки и tag одной операцией:

```text
git tag sdd-template-X.Y.Z
python .tools/sdd-template-release/verify_release.py --published
git push --atomic origin HEAD:main refs/tags/sdd-template-X.Y.Z
```

Это справочная последовательность для разработчика. Агент предлагает следующую команду
только после проверки результата предыдущей согласно `git.H4.4`.

Создать локальный пакет для проверки:

```text
python .tools/sdd-template-release/build_release.py --write
```

В проекте-потребителе установщик запускается из одноразового клона в
системном временном каталоге ОС. Родительская папка имеет имя
sdd-template-update-<32 hex>, клон — sdd-template-source-X.Y.Z-<8 hex commit>.
Клонируется immutable ref выбранного релиза с глубиной 1, а не произвольный
main. Запуск установщика выполняется один раз с --action init или --action update
и --write.

Установщик автоматически проверяет ref и commit клона, package manifest и SHA-256,
границы записи, структуру проекта, пользовательские файлы и ссылки. Краткий
отчёт показывает результат и только блокирующие конфликты. Полный inventory
выводится по --report full. Предварительный dry-run и повторные ручные проверки
не требуются. При реальном конфликте запись останавливается до затрагивания
спорных данных и отчёт содержит конкретный следующий шаг.

После успешного обновления удаляется только проверенный клон, созданный для этой
операции. При прерывании его можно повторно использовать. Установщик не очищает
весь системный temp, папку проекта tmp/ или сторонние каталоги. Пользовательские
изменения, неизвестные файлы и неоднозначные ссылки сохраняются и требуют решения.

Пути в тексте вычисляются от FRAMEWORK_ROOT. Markdown-ссылки на старые версии
переносятся на текущую проверенную версию только при наличии цели и совпадении
контрольной суммы документа. Symlink и junction sdd-template-current не создаются.
Source-only установщик, `.tools/fs_boundary.py` и его тесты исключены из consumer
package. `.tools/sdd_runtime/fs_boundary.py` включён как безопасная runtime-
зависимость инструментов `ui-reference` и `plantuml-render`.

Перед записью установщик проверяет существующие `AGENTS.md` и
`.project-structure.json`. Полный старый `AGENTS.md` Framework без маркеров,
изменённый managed-раздел, повреждённые маркеры и структура мета-репозитория в
корне проекта считаются коллизиями. В этом случае установщик возвращает
`status: awaiting_user_confirmation`, подробные `agents.differences` или
`project_structure.differences` и не записывает спорный файл. После решения
пользователя передайте одно из подтверждённых действий:

```text
--agents-action migrate
--agents-action replace-legacy
--agents-action replace-managed
--agents-action keep
--project-structure-action migrate
--project-structure-action replace
--project-structure-action keep
```

`migrate` изменяет только доказанные Framework-owned ссылки и возвращает
машиночитаемый diff. Неоднозначные ссылки требуют отдельного подтверждения и не
перезаписываются автоматически. После записи запускается post-install validator:
он классифицирует ссылки как `valid`, `historical`, `project`, `stale`,
`missing`, `ambiguous` или `external` и не даёт
завершить установку успешным статусом при нерешённых локальных Framework-ссылках.
Та же проверка блокирует неверные `package_id`, `version`, `release_dir`,
SHA-256 файлов пакета и неизвестные файлы в установленном каталоге.

### Контракт классификации ссылок Framework

| Случай | Классификация | Действие при обновлении |
|--------|---------------|-------------------------|
| Текстовый путь через `FRAMEWORK_ROOT` | `valid` | Сохранить |
| Markdown URL через прежний `sdd-template-current` | `stale` | Мигрировать на проверенный версионный путь |
| Версионированный путь в действующем документе | `stale` | Мигрировать на стабильный адрес по точному плану |
| Путь к старому релизу в действующем документе | `stale` | Мигрировать только при доказанной принадлежности Framework и проверенной цели |
| Путь к отсутствующей действующей цели | `missing` | Блокировать завершение до исправления |
| Историческое упоминание в `.tasks/done/`, `.issues/done/` или `docs/CHANGELOG.md` | `historical` | Сохранить исходную версию |
| Legacy-путь, принадлежащий только проекту | `project` | Сохранить |
| Legacy-путь с недоказанной принадлежностью или через reparse point | `ambiguous` | Не заменять автоматически; вернуть конфликт |
| Внешний URL с путём Framework | `external` | Не переписывать локальным мигратором |

Текстовые пути и кликабельные Markdown-ссылки обрабатываются отдельно. Для
Markdown разрешай относительный URL от каталога исходного документа и декодируй
`%20` как пробел в имени цели; буквальный `FRAMEWORK_ROOT` внутри URL не
подставляется. Ошибка чтения или декодирования проверяемого документа является
ошибкой проверки. Замена всех совпадений без классификации запрещена.

Если post-install проверка нашла доказанные действующие пути, результат содержит
`reference_migration`: точные замены с файлом, позицией, старым и новым
значением и SHA-256 исходного файла. При отсутствии неоднозначностей установщик
применяет план и повторяет проверку; изменение документа после построения плана
блокирует запись. Действующие Markdown URL переходят на проверяемый
проверенный версионный каталог, текстовые пути — на `FRAMEWORK_ROOT`.
Архивные ссылки и пользовательский текст вне точных фрагментов сохраняются.

Добавление нового managed-раздела поверх старых полных инструкций Framework
без подтверждения запрещено. При отсутствии корневого `.project-structure.json`
создаётся структура проекта-потребителя с путями через
`.agents/sdd-template-X.Y.Z`, а не копия структуры мета-репозитория.

## CLI

Установщик принимает --source-root, --target-root, --action init|update|use и
--write. Для use требуется --version. Источник должен быть клоном immutable ref,
зарегистрированного в release-registry.json. Операция init/update запускается
одним вызовом с --write после получения источника.

По умолчанию --old-action auto: чистая предыдущая версия удаляется только после
проверки post-install; при пользовательских данных или исторических ссылках она
сохраняется. Для явного восстановления доступны действия keep, move и delete с
inventory fingerprint. Параметры --cleanup-action и --cleanup-fingerprint нужны
только для возобновления отдельного сценария очистки. Параметры --agents-action
и --project-structure-action применяй только при конфликте соответствующих
managed-файлов. --report full выводит полный inventory.

## Размещение и границы записи

Source clone создаётся в системном temp в уникальном каталоге
sdd-template-update-<32 hex>/sdd-template-source-X.Y.Z-<8 hex commit>. Staging
пакета располагается во вложенном tmp самого клона. Удаляется только проверенный
клон операции; общий системный temp, проектный tmp и соседние каталоги не
затрагиваются.

В проект копируется только release package. Источники установщика,
.tools/fs_boundary.py и тесты не входят в release; runtime helper
.tools/sdd_runtime/fs_boundary.py входит как зависимость поддерживаемых tools. Каталог
.agents/sdd-template-current не создаётся. Ссылки в документах сверяются с
framework.release_dir; проверенные устаревшие ссылки переносятся точечно по
плану с SHA-256 исходного файла. Неизвестные файлы и изменения проекта
сохраняются, а конфликт блокирует только требующую решения операцию.
