## Дополнения SDD Framework для проекта-потребителя

Эти правила относятся к работе с технической документацией проекта.

## Корень Framework

Определи `FRAMEWORK_ROOT` по полю `framework.release_dir` корневого
`.project-structure.json`. Перед использованием проверь
`FRAMEWORK_ROOT/release-manifest.json` и SHA-256 файлов установленного релиза.
Пути к манифестам, шаблонам, подходам и инструментам Framework вычисляй от
`FRAMEWORK_ROOT`. Документы проекта создавай в корневых каталогах проекта,
указанных ниже.

## Документация проекта

- `FRAMEWORK_ROOT/.requirements/` — read-only шаблоны и методики.
- `docs/requirements/` — итоговые требования, которые создаёт разработчик.
- `.tasks/` — текущие задачи и планирование.
- `.issues/` — проблемы и дефекты проекта.
- `FRAMEWORK_ROOT/.manifest/` — правила работы с соответствующей областью.
- `README.md` — обзор проекта.

Соблюдай выбранный манифест и правила иерархии из
`FRAMEWORK_ROOT/.manifest/hierarchymanifest.md`. Различай текстовые пути и
кликабельные Markdown-ссылки: текстовые пути вычисляй от `FRAMEWORK_ROOT`, а
кликабельные ссылки на файлы Framework делай относительными; в них может быть
указан каталог активного релиза. При обновлении меняй только ссылки, доказанные
проверенным планом установщика. Правила определения версии продукта проекта см. в
`FRAMEWORK_ROOT/.manifest/versionmanifest.md`.

Не меняй версии ссылок поиском-заменой, в том числе временно для прохождения
предварительной проверки или после обновления. Применяй только точные изменения
из проверенного `reference_migration`-плана установщика с совпадающим fingerprint
исходного документа. Если нужного плана нет или он неоднозначен, останови только
миграцию ссылок, сообщи конкретные пути и запроси решение разработчика.

## Ясные ответы и вопросы

Начинай ответ с прямого результата или состояния. Если применимой инструкции
нет и решение нельзя обосновать источниками проекта, явно назови пробел, задай
один понятный вопрос и предложи безопасную альтернативу, основанную на доступных
источниках. Укажи, какое решение требуется от разработчика и что ты сделаешь
после ответа. Не выдавай предположение за правило проекта и не задавай вопрос
повторно, если ответ уже есть в контексте.

## Размещение результатов

| Шаблон | Результат |
|---|---|
| `FRAMEWORK_ROOT/.requirements/предметная область.md` | `docs/requirements/предметная область.md` |
| `FRAMEWORK_ROOT/.requirements/требования/*.md` | `docs/requirements/требования/<имя-документа>.md` |
| `FRAMEWORK_ROOT/.requirements/домены/*.md` | `docs/requirements/домены/<имя-документа>.md` |
| `FRAMEWORK_ROOT/.requirements/сценарии/*.md` | `docs/requirements/сценарии/<domain>/<имя-документа>.md` |

Путь и расширение результата обязательны. Выбирай точное имя по соглашению
проекта, затем по процедуре Framework; не переименовывай существующий результат
только ради шаблона. `.gitkeep` добавляй только в пустой каталог, который нужно
сохранить в Git.
