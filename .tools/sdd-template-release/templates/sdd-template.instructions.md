# SDD Framework — работа с документацией проекта

Эта инструкция относится к релизу `{{VERSION}}` с идентификатором `sdd-template`.
Источник: `Druk83/sdd-template.git`.

## Области путей

Корень установленного фреймворка в проекте-потребителе берётся только из
`framework.release_dir` корневого `.project-structure.json`:

```text
FRAMEWORK_ROOT=<значение framework.release_dir>
```

Проверь `release-manifest.json` и SHA-256 выбранного пакета. Во время
прерванного обновления может временно существовать ещё один версионированный
пакет; активным считай только каталог из `framework.release_dir` после проверки.
Symlink и junction не создавай. Текстовые пути разрешай от `FRAMEWORK_ROOT`,
а доказанные кликабельные ссылки мигрируй установщиком по проверенному плану.
Registry и chatlog находятся
по путям `FRAMEWORK_ROOT/.tools/registry.json` и `FRAMEWORK_ROOT/.chatlog/`.
Сокращённые пути каталогов фреймворка внутри его документации разрешаются
относительно `FRAMEWORK_ROOT`, а не относительно корня проекта. Результаты
работы записываются в корень проекта: `.source/`, `docs/`, `.tasks/` и
`.issues/`. Каталог `docs/requirements/` является рабочим каталогом проекта, а не
частью релиза: его существующее содержимое не копируется, не переносится и не
перезаписывается. Журналы самого Framework записываются только по явному запросу
разработчика в `FRAMEWORK_ROOT/.chatlog/`; корневой `.chatlog/` для Framework
не создаётся.

## Имена результатов документации

Для результатов в `docs/requirements/` обязательны каталог, определённый
процедурой, и расширение `.md`. Глобальная маска `*.md` не задаёт точное имя
файла.

При выборе имени соблюдай следующий порядок:

1. соглашение и уже используемые имена проекта;
2. явное имя из раздела `Выходные данные` выбранной процедуры H6, если оно указано;
3. новое описательное имя, согласованное с разработчиком.

Не переименовывай существующий документ из-за имени шаблона. Русские имена
документов допустимы, если они соответствуют языку и соглашению проекта;
`kebab-case` применяется к исходному коду, идентификаторам и новым
англоязычным именам, но не требует переименования русской документации.
`.gitkeep` создавай только для пустого каталога, который нужно сохранить в
Git; в каталоге с документами он не нужен.

При запуске инструмента из установленного пакета всегда используй полный путь,
например:

```text
python <FRAMEWORK_ROOT>/.tools/pdd/pdd_scan.py --format md
```

## Правила размещения

Релиз устанавливается в непосредственную дочернюю папку `.agents/`:

```text
.agents/sdd-template-X.Y.Z/
```

После завершения обновления в проекте-потребителе хранится одна активная папка
версии SDD Framework. Symlink и junction не создаются. При прерывании второй
проверенный пакет может временно оставаться до восстановления по
`framework.release_dir`. Другие каталоги `.agents/` принадлежат проекту и не
изменяются.

`AGENTS.md` пользователя не входит в релиз и никогда не заменяется целиком.

## Установка и обновление Framework

Команды `инициализируй сдд`, `обнови сдд` и `вернись на версию X.Y.Z` относятся
только к этому Framework. При явной команде установки или обновления получи
актуальную процедуру из исходного репозитория `Druk83/sdd-template`. Не выводи
шаги установки из документации установленного пакета и не выполняй их при
обычной работе. Инструменты сопровождения и полная процедура обновления в этот
пакет не входят.

## Профиль требований этапа [3]

Перед составлением требований прочитай
`FRAMEWORK_ROOT/.manifest/requirementsprofilemanifest.md` и каталог
`FRAMEWORK_ROOT/.requirements/требования/профили.json`. Выбор `requirements_profile`
записывается на этапе [2] в `docs/requirements/обоснование выбора.md`.
Для проверки выбора и результата используй переносимый инструмент
`FRAMEWORK_ROOT/.tools/requirements-profile/requirements_profile.py` с
`--project-root`, указывающим корень проекта. Старые решения по ГОСТ 19/34
обрабатывай по правилу совместимости; перевод содержимого в версии 1.9.3
не выполняется.

## UI-подэтап и reference artifacts

Перед работой с пользовательским интерфейсом прочитай:

- `FRAMEWORK_ROOT/.manifest/uimanifest.md`;
- `FRAMEWORK_ROOT/.approach/ui-pattern-selection.md`;
- `FRAMEWORK_ROOT/.requirements/пользовательский-интерфейс/README.md` и связанные
  процедуры пользовательского интерфейса.

Используй только официальный внешний каталог:

`https://github.com/Druk83/ui-patterns.git`

UI-подэтап выполняется после сценариев и до структуры данных. Сначала сформируй
`screen pool`, затем предложи viewport matrix, pattern candidates, screen
specifications и live reference prototypes. Каждый зависимый переход требует
отдельного подтверждения разработчика. При отсутствии UI используй `gap` до решения
и `not_applicable` только после подтверждённого отсутствия UI.

По умолчанию результаты проекта размещаются в
`docs/requirements/пользовательский-интерфейс/`:

```text
docs/requirements/пользовательский-интерфейс/
├── манифест-спецификации-интерфейса.json
├── пул-экранов.json
├── screens/<screen-id>.md
└── references/<reference-set>/
    ├── screen-manifest.json
    └── <viewport-orientation>/
        ├── index.html
        ├── reference-manifest.json
        ├── README.md
        ├── <screen-artifact>.html
        └── assets/
```

Prototype является `reference-only`, работает offline на fixture data и не содержит
project API, secrets или production data. Production code создаётся отдельным этапом.

Перед миграцией или очисткой legacy `docs/.figma` выполни inventory и diff, покажи
пользователю нестандартные файлы и не удаляй источник без отдельного подтверждения.
Используй portable-инструмент `ui-reference` из установленного Framework для
валидации и безопасной миграции.
