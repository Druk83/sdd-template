# SDD Framework — установка и обновление

Эта инструкция относится к релизу `{{VERSION}}` с идентификатором `sdd-template`.
Источник: `Druk83/sdd-template.git`.

## Области путей

Корень установленного фреймворка в проекте-потребителе:

```text
FRAMEWORK_ROOT=.agents/sdd-template-{{VERSION}}
```

Сокращённые пути каталогов фреймворка внутри его документации разрешаются
относительно `FRAMEWORK_ROOT`, а не относительно корня проекта. Результаты
работы записываются в корень проекта: `.source/`, `docs/`, `.tasks/` и
`.issues/`. Каталог `docs/requirements/` является рабочим каталогом проекта, а не
частью релиза: его существующее содержимое не копируется, не переносится и не
перезаписывается. Журналы самого Framework записываются только по явному запросу
разработчика в `FRAMEWORK_ROOT/.chatlog/`; корневой `.chatlog/` для Framework
не создаётся.

## Имена результатов документации

Для результатов в `docs/requirements/` обязательны каталог, определённый
процедурой, и расширение `.md`. Глобальная маска `*.md` не задаёт точное имя
файла.

При выборе имени соблюдай следующий порядок:

1. соглашение и уже используемые имена проекта;
2. явное имя из раздела `Выходные данные` выбранной процедуры H6, если оно указано;
3. новое описательное имя, согласованное с разработчиком.

Не переименовывай существующий документ из-за имени шаблона. Русские имена
документов допустимы, если они соответствуют языку и соглашению проекта;
`kebab-case` применяется к исходному коду, идентификаторам и новым
англоязычным именам, но не требует переименования русской документации.
`.gitkeep` создавай только для пустого каталога, который нужно сохранить в
Git; в каталоге с документами он не нужен.

При запуске инструмента из установленного пакета всегда используй полный путь,
например:

```text
python .agents/sdd-template-{{VERSION}}/.tools/pdd/pdd_scan.py --format md
```

## Правила размещения

Релиз устанавливается в непосредственную дочернюю папку `.agents/`:

```text
.agents/sdd-template-X.Y.Z/
```

В проекте-потребителе хранится только одна папка SDD Framework. Другие каталоги
`.agents/` принадлежат проекту и не изменяются.

`AGENTS.md` пользователя не входит в релиз и никогда не заменяется целиком.

## Короткие команды

Распознавать следующие русские команды только после подтверждения, что работа
относится к `SDD Framework` с `package_id: sdd-template` и источником
`Druk83/sdd-template.git`:

| Команда пользователя | Нормализованная операция |
|---|---|
| `инициализируй сдд` | `sdd-template:init` — установить `default_version` из реестра |
| `обнови сдд` | `sdd-template:update` — установить `default_version` из реестра |
| `вернись на версию X.Y.Z` | `sdd-template:use X.Y.Z` — установить запись версии из реестра |

Команда `sdd-template:use X.Y.Z` применяется и для обновления, и для даунгрейда.
Направление определяется сравнением текущей и целевой версий. В чистом проекте
одноразово требуется команда `инициализируй сдд из Druk83/sdd-template.git`;
после установки источник определяется этой инструкцией.

Если источник не подтверждён, общие фразы с «сдд» не считать командами этого
Framework и не выполнять установку.

## Первичная подготовка корня проекта

После подтверждения первичной установки проверь рабочие каталоги в корне
проекта. Отсутствующие элементы стандартного каркаса добавь; существующие
файлы и содержимое пользователя не перезаписывай. Для существующего
`.gitignore` добавь только отсутствующие правила в блоке
`SDD Framework: managed ignore entries`, не изменяя пользовательские строки:

```text
.source/
  README.md
.tasks/
  README.md
  done/
  pdd/
    @todoregistry.md
.issues/
  README.md
  done/
docs/requirements/
```

`docs/requirements/` обрабатывается отдельно: если каталог уже существует,
сохрани его полностью, включая все файлы, подкаталоги и пользовательские
изменения. Не копируй в него содержимое `.requirements/` релиза и не перемещай
его в корень проекта. Если каталога нет, создай только сам каталог и
`.gitkeep`, чтобы пустой каталог был виден Git.

Каталог `.chatlog/` в корне проекта на этом шаге не создавай: для журналов
Framework используется `FRAMEWORK_ROOT/.chatlog/`.

Если файл отсутствует, создай его. Существующие файлы не перезаписывай:

- `.project-structure.json` — если файла нет, создай структуру проекта-потребителя
  с `FRAMEWORK_ROOT=.agents/sdd-template-X.Y.Z`; не копируй в корень структуру
  мета-репозитория. Если файл существует, сохрани его и проверь расхождения.
- `.gitignore` — создай с правилами для `.project-structure.json`, `tmp/`,
  `.source/`, `.tasks/done/`, `.issues/done/` и `.agents/sdd-template-*/`;
- `.editorconfig` — создай с кодировкой UTF-8, LF и завершающим переводом строки;
- `.gitattributes` — создай со строкой `* text=auto eol=lf`;
- `README.md` — создай пустым.

При наличии корневого `AGENTS.md` не заменяй его и не изменяй вне управляемого
раздела после отдельного подтверждения пользователя. Перед установкой проверь,
не содержит ли файл старые полные инструкции Framework без маркеров. Не добавляй
новый раздел поверх такого текста автоматически: покажи расхождение и запроси
`replace-legacy` или `keep`.

## Проверка доступной версии

Минимальная поддерживаемая версия — `{{MIN_SUPPORTED_VERSION}}`. Версии ниже
`{{MIN_SUPPORTED_VERSION}}` не адаптированы к
сборщику и не устанавливаются, не обновляются и не используются для автоматического
возврата.

1. Определить корень текущего проекта.
2. Получить только `README.md` и `release-registry.json` из корня ветки `main`
   репозитория `Druk83/sdd-template.git` без создания обзорного клона, например
   через raw-файл GitHub; ветка
   `main` используется здесь только как источник реестра, а не для выбора версии
   по `README.md`.
3. Для `init` и `update` выбрать `default_version` реестра. Для `use` найти точную
   запись запрошенной версии. Выбор версии через `main`, историю коммитов или имя
   случайной папки запрещён.
4. Использовать из выбранной записи только `ref`, `ref_type` и `install_path`.
   Для `ref_type: tag` точный commit проверять после клонирования; для
   `ref_type: commit` сверить `ref` и `commit`.
5. Получить выбранный источник и прочитать его главный `README.md`. Проверить, что
   версия не ниже `{{MIN_SUPPORTED_VERSION}}` и совпадает с записью реестра.
6. При версии ниже `{{MIN_SUPPORTED_VERSION}}` остановиться и сообщить, что исходники не адаптированы
   к сборщику.
7. Проверить только непосредственные дочерние папки `.agents/` с именем
   `sdd-template-X.Y.Z`.
8. Сравнить доступную версию с версией в имени локальной папки.

Рекурсивное сканирование репозитория и чтение вложенных README для первичного
определения версии не выполняются.

Если версии совпадают, обновление не требуется. При этом можно проверить наличие
`sdd-template.instructions.md` и согласованность `release-manifest.json`.

## Получение релиза

При отличии версий клонировать выбранный по реестру `ref` только в каталог
`tmp/` текущего проекта. Для явно выбранного commit или tag использовать
отдельное имя с указателем источника, например:

```text
<корень проекта>/tmp/sdd-template-source-X.Y.Z-<short-commit>/
```

Для получения выбранной записи реестра используется имя
`tmp/sdd-template-source-X.Y.Z-<short-commit>/`, где `<short-commit>` — первые
8 символов фактического commit клона. Каталог `.sdd-template-source/` в корне
проекта не используется. Клон должен быть мелким (`--depth 1`) и содержать
только выбранный `ref`. Предварительный каталог `.sdd-template-review/` не
создаётся.
Если временная папка уже существует, её нельзя
перезаписывать; операцию остановить и запросить решение пользователя.

Системная временная папка ОС не используется. Существующая временная папка не
перезаписывается: при коллизии операция останавливается и запрашивает решение.

После клонирования запустить установщик из чистой копии:

```text
python tmp/sdd-template-source-X.Y.Z-<short-commit>/.tools/sdd-template-release/install_framework.py --source-root tmp/sdd-template-source-X.Y.Z-<short-commit> --target-root . --action <action> --write
```

`<action>` принимает `init`, `update` или `use`. Параметр `--version` используется
только с `use`. Установщик сам берёт точный `ref` и `install_path` из реестра;
передавать ref вручную или копировать исходный корень запрещено.

Для `use` добавить `--version X.Y.Z`. При замене существующего релиза после
подтверждения пользователя добавить `--old-action move`, `--old-action delete` или
`--old-action keep`. Для `move` и `delete` после просмотра inventory передать его
fingerprint через `--old-confirmation <old-inventory-fingerprint>`.

Параметр `--target-root .` явно задаёт корень проекта-потребителя. Установщик создаёт
готовый пакет непосредственно в корне проекта:

```text
.agents/sdd-template-X.Y.Z/
```

Промежуточная сборка установщика создаётся внутри каталога клона источника, в его
локальном `tmp/sdd-template-build-X.Y.Z/`. Второй каталог рядом с клоном в
корневом `tmp/` не создаётся. Если staging уже существует после прерванной
записи, установщик автоматически проверяет его версию, ref и commit и использует
совместимый staging повторно. Несовместимый или повреждённый staging не
перезаписывается.

Проверить имя папки, README релиза, `release-manifest.json`, состав и контрольные
суммы. При несовпадении остановиться. Запрещено копировать корень исходного
репозитория или содержимое `tmp/sdd-template-source-X.Y.Z-<short-commit>/` в корень
проекта.

## Установка и обновление

Если старой папки SDD Framework нет, после проверки запросить подтверждение
первичной установки и запустить установщик с действием `init`.

Если старая папка есть, сначала получить inventory старого release и показать пользователю
обе версии, fingerprint, сводку и полный список нестандартных путей. Новый release должен
быть собран и проверен до destructive operation. После отдельного ответа пользователя
выполнить только выбранное действие:

- оставить старую версию и завершить операцию;
- удалить старую папку;
- переместить старую папку в `tmp/sdd-template-old-X.Y.Z/`.

После ответа передать установщику подтверждённое действие через `--old-action` и для
`move`/`delete` fingerprint через `--old-confirmation`. Установщик создаёт только новую папку
`.agents/sdd-template-X.Y.Z/` после успешной сборки, а старую папку изменяет только после
успешной проверки нового package. Не перезаписывать корневой `.agents/`, другие
каталоги и существующую целевую папку без отдельного подтверждения.

Если найдено более одной папки `sdd-template-*`, остановиться и сообщить о конфликте.

## Возврат к сохранённой версии

Возврат разрешён только к пакету, который пользователь ранее сохранил в
`tmp/sdd-template-old-X.Y.Z/` или в другой явно указанной папке корня проекта.
Проверить имя папки, версию в её `README.md` и `release-manifest.json`, показать
результат пользователю и запросить подтверждение.

После подтверждения текущую папку `.agents/sdd-template-X.Y.Z/` сначала переместить
в новую свободную папку внутри `tmp/`, затем переместить сохранённый пакет в
`.agents/`. Не изменять другие каталоги `.agents/`, содержимое `tmp/` и
пользовательский `AGENTS.md`. Если сохранённого пакета нет, остановиться и сообщить,
что для возврата нужен архив старой версии или другой явно указанный локальный источник.

## Подключение через `AGENTS.md`

После установки создай корневой `AGENTS.md`, если его нет, и добавь в него только
этот управляемый раздел. Внутри раздела размести полный текст канонического
`AGENTS.md` из источника `Druk83/sdd-template.git`. Если файл уже существует,
сохрани весь его текст вне раздела и добавь управляемый раздел в конец:

```text
<!-- SDD Framework: managed section begin -->
<полный текст канонического AGENTS.md Framework>
<!-- SDD Framework: managed section end -->
```

Изменять разрешено только содержимое между маркерами либо добавление раздела в
конец существующего файла. При одной корректной паре маркеров весь управляемый
раздел заменяется актуальным каноническим текстом Framework. Ручные изменения
внутри управляемого раздела не считаются пользовательскими инструкциями и могут
быть заменены; индивидуальные инструкции размещаются вне этого раздела.
Перед записью и после неё проверить, что весь пользовательский текст вне
управляемого раздела не изменился. При повреждённых или нескольких маркерах,
либо при явном запрете пользователя, раздел не перезаписывать и сообщить о
конфликте. Если полный старый файл Framework распознан без пользовательского
текста, после подтверждения разрешено заменить его целиком на один managed-раздел.
Если пользовательский текст смешан со старым Framework и границы не определяются,
автоматическая замена запрещена.

Результат установки содержит поле `agents` со статусом `created`, `updated`,
`unchanged`, `replaced`, `kept` или `conflict`, список `agents.conflicts` и
подробности `agents.differences`. Если список не пуст, сообщить пользователю
все перечисленные коллизии и не считать подключение полностью согласованным до
их решения. Для решения передай установщику только подтверждённое действие:

```text
--agents-action replace-legacy
--agents-action replace-managed
--agents-action keep
```

Установщик возвращает `status: awaiting_user_confirmation` до выбора действия
и не изменяет `AGENTS.md` при значении `ask`.

## Проверка `.project-structure.json`

В проекте-потребителе корневой `.project-structure.json` описывает проект и
ссылается на ресурсы Framework через `FRAMEWORK_ROOT`. Структура мета-репозитория
с обязательными корневыми `.manifest`, `.requirements` и `.tools` не переносится
в корень потребителя. Если обнаружено такое расхождение, покажи его пользователю
и запроси одно из действий:

```text
--project-structure-action replace
--project-structure-action keep
```

`replace` разрешён только для известного шаблона мета-репозитория; произвольный
пользовательский файл автоматически не заменяется.

## Очистка `tmp/`

После проверки результата операция не считается завершённой, пока агент явно не
задаст пользователю вопрос об очистке. В ответе обязательно перечислить один
созданный каталог клона и указать, что вложенный staging удалится вместе с ним:

```text
Создан временный каталог:
tmp/sdd-template-source-X.Y.Z-<short-commit>/
Внутри него находится промежуточная сборка.
Удалить этот каталог после проверки? Ответьте «да» или «нет».
```

До ответа статус операции — `installed_pending_cleanup`, а статус очистки —
`awaiting_user_confirmation`. Агент обязан показать пользователю значение `cleanup.question`,
`next_action.message`, fingerprint, сводку и полный список нестандартных данных и не называть
операцию завершённой до этого ответа. После ответа повторно запустить установщик с тем же
`--source-root` и одним из действий:

```text
python tmp/sdd-template-source-X.Y.Z-<short-commit>/.tools/sdd-template-release/install_framework.py --source-root tmp/sdd-template-source-X.Y.Z-<short-commit> --target-root . --cleanup-action delete --cleanup-fingerprint <cleanup-inventory-fingerprint>
```

При ответе «нет» использовать `--cleanup-action keep`. Без fingerprint удаление не
выполняется; при изменении inventory после подтверждения оно блокируется. Режим очистки
разрешает удалять только указанный каталог клона целиком, включая его вложенный staging.
Весь `tmp/`, старые релизы и чужие временные данные не удалять.
