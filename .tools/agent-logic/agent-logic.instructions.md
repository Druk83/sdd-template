# Инструкции для агента agent-logic

## Установка готового пакета

Если пользователь указал каталог готового экспорта `agent-logic`, считайте его проверенным переносимым пакетом.

1. Скопируйте каталог целиком в `.tools/agent-logic` проекта-потребителя.
2. Добавьте без изменений содержимое `registry-entry.json` в `.tools/registry.json`.
3. Прочитайте путь из поля `instructions` добавленной записи реестра.
4. Проверьте `manifest.json` и запустите точку входа из реестра с `--help`.

Запрещено пересоздавать, генерировать по аналогии или переписывать исходный код, wrappers, README и манифест пакета. Создание нового экспорта выполняется только упаковщиком в исходном репозитории инструмента.

Если `.tools/agent-logic` уже существует, не заменяйте его без явного разрешения пользователя. Сначала сообщите о конфликте версии или содержимого.

## Обязательная проверка по запросу пользователя

Если пользователь просит проверить или проанализировать документ, агент обязан создать Markdown-отчёт проверки в `tmp/agent-logic/.runtime/exports/<compilationId>/`. Файл отчёта не создаётся в `.tasks/` и не заменяет существующий результат.

1. Сохраните исходный текст запроса и время его регистрации в ISO 8601 со смещением UTC.
2. Запустите `compile` с `--format md`, `--request`, `--requested-at`, явными `--output` и `--write`.
3. Путь `--output` должен находиться только в `tmp/agent-logic/.runtime/exports/<compilationId>/`.
4. Не добавляйте `--replace`, если пользователь отдельно не разрешил замену существующего отчёта.
5. В сообщении человеку укажите путь к созданному отчёту, его статус и краткий вывод из `agent_context.user_guidance`.
6. Если `user_guidance.mode=NO_ACTION_REQUIRED`, прямо сообщите: «Действия по результату проверки не требуются». Не ищите, что можно исправить дополнительно.
7. Если `user_guidance.mode=REVIEW_REQUIRED`, перечислите только `required_actions`: правило, источник и безопасный следующий шаг.
8. Если `user_guidance.mode=HUMAN_DECISION_REQUIRED`, задайте только `human_question` и приведите карточку решения; не выбирайте вариант и не предлагайте редакторскую замену текста.
9. Для карточки `review_hypothesis` покажите человеку варианты, различия и последствия. Допустимо только передать ответ `approved`/`rejected` с выбранным вариантом; `CHANGE` означает новую трактовку или дополнительный вопрос, а не правку источника.
10. `observations` являются справочным контекстом. Запрещено выдавать их за ошибку, GAP, обязательное действие, вопрос человеку или рекомендацию правки. Не изменяйте исходный документ автоматически.

## Обязательный локальный методический слой ASIR

Команда `logic-review` в версии 0.5.1 передаёт в `logic-review.request.json`
поле `method_pack`. Внутри находятся локальные промпт, алгоритм и спецификации
`понятия`,
`суждения`, `силлогизмы`, `индукция`, `логические_ошибки`, `законы_мышления` с SHA-256.

Перед формированием ответа прочитайте `method_pack.system_prompt`, затем все
спецификации, перечисленные в `method_pack.specifications`. Следуйте каждому
шагу `method_pack.algorithm`; для неприменимого шага укажите
`not_applicable` и причину. Не ограничивайте каталог логических ошибок кодами
ASIR: поле `code` открыто, но ошибка обязана иметь русское и латинское имя.

Поле `method_pack.reference_materials` указывает необязательный справочник
`.tools/agent-logic/agent_logic/logic_specs/методический справочник логической проверки.md`.
Используйте его для формирования `expert_review`: открывайте только раздел,
связанный с текущей неоднозначностью или типом вывода. Не загружайте весь
справочник в каждый запрос, не заменяйте им спецификации и не добавляйте его
содержание в результат как отдельные факты. Путь находится внутри самого
пакета и не требует доступа к исходному ASIR или к сети.

Результат должен содержать контракт `asir.logic_review_result` версии `0.2`,
совпадающий `request_id` и `method_manifest`, а также полный блок:

- `expert_review.verdict`;
- `argument_structure` с тезисами, посылками, выводами и переходами;
- `findings` с `family`, `name_ru`, `name_latin`, `truth_scope`, provenance,
  объяснением, скрытыми посылками, последствиями и предложением исправления;
- `hidden_premises`, `non_deductive_strength`, `limitations`.

В режиме `review` не редактируйте исходный текст. `suggested_fix` — только
рекомендация для карточки решения. Даже формально корректный вывод не означает
материальную истинность посылок. Не добавляйте в ответ `facts`, `proved`,
`actions`, `execution_policy` или `ai_risk_score`.

## Формат согласованных редакторских правок

Если пользователь явно просит исправить проверяемый текст по схеме с кавычками и квадратными скобками, каждое изменяемое утверждение оформляйте непосредственно в исходном документе так:

```text
"исходный ошибочный или неточный фрагмент" [исправленный фрагмент]
```

Сохраняйте исходный фрагмент без изменений внутри двойных кавычек, сразу после него помещайте согласованную редакцию в квадратных скобках. Не называйте утверждение ошибочным без основания проверки: для спорного фрагмента сохраняйте исходную формулировку и добавляйте уточнение, явно обозначенное пользователем. Не переписывайте соседний контекст и не превращайте гипотезу в факт. После правки повторно проверьте документ и перечислите изменённые фрагменты с их строками.

Пример структуры вызова:

```text
python .tools/agent-logic/agent-logic.py compile <путь-к-документу> --format md --request <исходный-запрос> --requested-at <ISO-8601> --output tmp/agent-logic/.runtime/exports/<compilationId>/<имя>.agent-logic.md --write
```

Если применимые правила проекта-потребителя запрещают создание файла без отдельного разрешения, сообщите это человеку и покажите команду; не обходите правила верхнего уровня.
