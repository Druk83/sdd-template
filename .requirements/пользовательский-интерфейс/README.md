# Техническая документация пользовательского интерфейса (UI)

Методика создаёт проектный UI-пакет в `docs/requirements/пользовательский-интерфейс/`. Пакет включает пул экранов, спецификации и эталонные прототипы; он не является рабочей реализацией продукта.

Источник UI-паттернов — только опубликованный каталог `https://github.com/Druk83/ui-patterns.git`. В каждом пакете фиксируй версию и точную ревизию каталога; локальный путь checkout не включай в результат.

## Режимы работы

Поле `workflow_mode` в `пул-экранов.json` и `манифест-спецификации-интерфейса.json` задаёт один из режимов:

- `early-prototype` — исследование и прототипирование разрешены до завершения этапов `[1]`–`[5]`. Создавай пакет в статусе `proposed`, используй `.source/` и ответы разработчика, явно фиксируй предположения и GAP. Отсутствие требований, сценариев или подтверждённых размеров не блокирует работу и не разрешает выдумывать решения.
- `track-integrated` — сверка раннего результата с требованиями, сценариями и критериями приёмки при прохождении `[5.a]`. Обновляй тот же пакет на месте, сохраняя происхождение и историю решений.

Оба режима используют один канонический путь. Вторую staging-копию не создавай. Этап `[5.a]` можно запустить независимо от позиции в треке; в самом треке он расположен после сценариев и до структуры данных.

## Последовательность

1. Определи применимость UI: подтверждённое наличие, `gap` при нехватке сведений или `not_applicable` после явного подтверждения отсутствия интерфейса.
2. Зафиксируй опубликованную версию и точную ревизию внешнего каталога.
3. Инвентаризируй источники и предложи пул экранов. Для каждого исходного кандидата зафиксируй экран, состояние, объединение, обоснованное исключение или GAP.
4. Предложи роли, состояния, паттерны, шаблоны и viewport. Не превращай универсальные шаблоны каталога в обязательные экраны продукта.
5. Получи решения разработчика; до подтверждения оставляй их `proposed`.
6. Создай отдельную спецификацию каждого включённого экрана и свяжи её с требованиями, сценариями и критериями, если они существуют.
7. Создай эталонный прототип. Для каждого представления явно свяжи `screen_id`, спецификацию, роль, состояние, viewport и файл.
8. Запусти `ui-reference validate --package` и отдельно проведи визуальную проверку. Валидатор проверяет структуру и связи, но не оценивает качество дизайна.

## Структура результата

```text
docs/requirements/пользовательский-интерфейс/
├── README.md
├── пул-экранов.json
├── манифест-спецификации-интерфейса.json
├── screens/
│   └── <screen-id>.md
└── references/
    └── <reference-set-id>/
        ├── screen-manifest.json
        └── screens/
            └── <screen-id>/
                └── <viewport-id>/
                    ├── index.html
                    ├── shell.css
                    ├── reference-manifest.json
                    └── README.md
```

Файлы схем и шаблоны для подготовки результата находятся в `.requirements/пользовательский-интерфейс/` и не копируются как проектные результаты. Схемы находятся в `схемы/`.

## Связь экранов и артефактов

В `манифест-спецификации-интерфейса.json` каждая включённая запись `screens[]` связывает `screen_id` со спецификацией, выбранными pattern/template IDs и списком `artifact_id`. В `screen-manifest.json` каждая запись `artifacts[]` указывает такой `artifact_id`, тот же `screen_id`, роль и состояние из пула, viewport-кандидат и безопасный относительный путь к файлу.

Если `template_set_version` пакета равен `0.3.1` или новее, provenance UI manifest, screen pool и каждого `screen-manifest.json` должна совпадать. Каждый viewport в пуле содержит непустой `screen_shell_candidates`: допускаются статусы `selected`, `proposed`, `rejected`, `gap` и `not_applicable`; `selected` может быть не более одного, несколько вариантов могут оставаться `proposed`. Точные варианты содержат URL каталога, закреплённую ревизию, `shell_id`, `shell_version`, `shell_viewport` и обоснование; геометрия должна совпадать с viewport. Для отсутствующей оболочки используй `gap`, для невизуального результата — `not_applicable` с обоснованием.

Каждая запись артефакта содержит `shell_binding`, который соответствует кандидату того же viewport в пуле. Для `selected`/`proposed` сверяются URL и точная ревизия репозитория каталога оболочек, `shell_id`, `shell_version` и геометрия; для `gap` — причина и требуемое решение. Для стандартной библиотеки Framework указывай `https://github.com/Druk83/sdd-template.git` и `source_commit` установленного пакета из `FRAMEWORK_ROOT/release-manifest.json`. Версия `ui-patterns` и её commit остаются отдельными корневыми полями UI-пакета; они также фиксируются в `screen-manifest.json` и сверяются с корневым манифестом. Сам `shell_id` и геометрия должны разрешаться по библиотеке `FRAMEWORK_ROOT/.tools/ui-screen-scaffold/shells/shell-library.json`; локальные пути к репозиторию Framework в проектные документы не включай. `ui-reference` сверяет ID, версию, геометрию и commit по библиотеке и `release-manifest.json`. Для новых записей `screen-manifest.json` `pattern_refs` и `template_refs` повторяют ссылки из записи того же экрана UI manifest; независимое редактирование этих массивов запрещено. Пакеты, сохраняющие историческую версию источника `0.3.0` или ниже, остаются валидными без новых полей; обновление версии источника требует явного пересмотра привязок, автоматической миграции нет. Для GAP viewport не указывай выдуманные размеры.

Для генерации оболочек заполни `screen-manifest.json` явными вариантами и запусти `python .tools/ui-screen-scaffold/ui_screen_scaffold.py generate --package docs/requirements/пользовательский-интерфейс --reference-set <reference-set-id>`. По умолчанию команда только строит план. Добавление `--write` создаёт автономные страницы в `references/<reference-set-id>/screens/<screen-id>/<viewport-id>/`. Перед записью команда проверяет экран, роль, состояние, viewport, выбранную оболочку и отсутствие конфликтующих выходных файлов. Она создаёт только нейтральный слот; содержимое экрана агент формирует отдельно по спецификации и явно выбранным ссылкам на паттерны/шаблоны. Генератор не выбирает паттерны, не придумывает продуктовые данные и не перезаписывает существующие материалы.

Если один файл визуально представляет несколько экранов или состояний, каждой записи добавь уникальный `target` (например, route или selector); в остальных случаях `target` не требуется. Один pattern/template ID можно использовать на нескольких разных экранах; дублирование кандидата внутри одного экрана запрещено.

Схемы `схемы/манифест-спецификации-интерфейса.schema.json`, `схемы/пул-экранов.schema.json` и `схемы/screen-manifest.schema.json` задают контракт версии `2`. В `screen-manifest` поля `shell_binding`, provenance и ссылки `pattern_refs`/`template_refs` обязательны для `ui-patterns` `0.3.1` и новее; их обязательность определяется версией набора в корневом манифесте UI-пакета. Инструмент также принимает контракт `1` как legacy-вход и не выполняет автоматическую миграцию файлов проекта.

## Применение прототипов

Прототип — автономный framework-neutral HTML/CSS/JS reference artifact с синтетическими данными. Он не использует project API, секреты или production data и не подменяет production UI. Рабочий код создаётся отдельным подтверждённым этапом.

При переносе `docs/.figma` и других legacy-каталогов выполняй inventory и diff. Не удаляй источник, не перезаписывай конфликты и не очищай неизвестные файлы без отдельного подтверждения пользователя.

## Инструмент

Проверить полный пакет:

```text
python .tools/ui-reference/ui_reference.py validate --package docs/requirements/пользовательский-интерфейс
```

См. [инструкцию манифеста UI](../../.manifest/uimanifest.md) и [README инструмента](../../.tools/ui-reference/README.md).

Генерация выбранных оболочек выполняется зарегистрированным инструментом
`ui-screen-scaffold`; сначала выполни dry-run, затем `--write` только после проверки
списка создаваемых файлов. После заполнения слота проверь пакет командой выше.
