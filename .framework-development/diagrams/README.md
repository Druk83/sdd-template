# Разработка SDD Framework: реестр диаграмм

Каталог описывает архитектуру и текущую разработку SDD Framework (AS-IS) для
разработчика мета-репозитория. Он не описывает работу агента в проекте-потребителе.
Каталог хранится в исходном репозитории, но исключён из consumer-пакета; его
содержимое не скрыто от читателей исходного репозитория.

Правила каталога заданы в
[`.manifest/frameworkdiagramsmanifest.md`](../../.manifest/frameworkdiagramsmanifest.md).
Публичные диаграммы процессов SDD остаются в [`.diagrams/`](../../.diagrams/).

## Реестр диаграмм

Реестр является перечнем обязательных архитектурных представлений. В нём
указано, что показывает каждая диаграмма и для какого вопроса она нужна.
Комплект содержит две BPMN-диаграммы для отдельных процессов и семь
архитектурных представлений в PlantUML. Дополнительные типы в этот комплект не
включены.

| Тип и файл | Что показывает | Для чего нужна |
|---|---|---|
| BPMN: [исходник](framework-development-process.bpmn), [PNG](framework-development-process.png) | Общие входы в работу Framework, исследование, решение о создании Issue или Task и переход к выполнению | Понять общий ход разработки и роли разработчика-создателя и агента |
| BPMN: [исходник](framework-issue-task-lifecycle.bpmn), [PNG](framework-issue-task-lifecycle.png) | Triage Issue, запрос данных, решение оставить исследование без Task или создать Task, блокировки и независимые критерии завершения Task и Issue | Разобрать переходы статусов и понять, когда внутренняя работа считается завершённой |
| SysML: диаграмма определения блоков (block definition diagram, BDD): [исходник](framework-sysml-block-definition.plantuml), [PNG](framework-sysml-block-definition.png) | Framework как систему блоков: правила, методики, учёт работ, инструменты, пакет и проект-потребитель | Разобрать состав системы и границы между её основными частями |

| UML: диаграмма классов (class diagram): [исходник](framework-artifact-classes.plantuml), [PNG](framework-artifact-classes.png) | Структуру Issue, Task, PDD-записи, выпуска и проекта-потребителя; отделяет версию Framework от версии продукта | Понять поля артефактов, их связи и независимые правила версионирования |

### Примечание о SysML BDD

PlantUML не предоставляет отдельную встроенную нотацию SysML. Диаграмма блоков
построена на синтаксисе PlantUML class diagram со стереотипом `<<block>>` и
показывает структуру и композицию блоков. Это PlantUML-представление диаграммы
определения блоков (block definition diagram, BDD), а не полный SysML-редактор.

## Правила ведения реестра

1. Для диаграмм указывай статус `AS-IS` и проверяемые источники внутри исходника.
2. Сохраняй один исходник и рядом PNG для каждой записи реестра. Исходник —
   главный артефакт, PNG — его проверенный рендер.
3. Обновляй реестр при добавлении, переименовании или удалении диаграммы.
   Не добавляй типы сверх перечисленных без предварительного обсуждения в чате
   и обоснования, какую отдельную задачу решит новый тип.
4. Используй не более двух BPMN-диаграмм. В текущем комплекте первая показывает
   общий процесс разработки Framework, вторая — отдельный жизненный цикл Issue и
   Task. Вторую включили, поскольку переходы статусов и критерии их закрытия
   требуют отдельного обзора. Не используй BPMN для архитектурных представлений.
5. При изменении правил, структуры или инструментов сверяй все затронутые виды
   архитектуры и обновляй их в рамках той же доработки.
6. Перед каждым релизным кандидатом сверяй весь реестр с реализацией и запиши
   результат в задаче или отчёте кандидата.
7. Если факт не подтверждён правилами или реализацией, обозначь пробел. Не
   достраивай предполагаемое поведение.

## Рендеринг

Из корня репозитория обнови PNG всех диаграмм каталога:

```powershell
python .tools/plantuml-render/plantuml_render.py --path .framework-development/diagrams/
```

Рендерер может требовать доступный локальный стек Kroki. После рендеринга
проверь читаемость каждого изображения и его соответствие исходнику. Внутренние
диаграммы не включай в явный список файлов consumer-экспорта.

## Источники правил

- `.manifest/frameworkdiagramsmanifest.md` — состав обязательных видов,
  разделение внутренних и потребительских диаграмм, синхронизация и рендеринг.
- `.manifest/issuesmanifest.md` и `.manifest/taskmanifest.md` — поля и процессы
  Issue и Task.
- `.manifest/pddmanifest.md` — связь кодовой записи `@todo` с Task и PDD-реестром.
- `.manifest/exportmanifest.md` и
  `.tools/sdd-template-release/build_release.py` — состав consumer-пакета.
- `.manifest/gitmanifest.md` и `.tools/sdd-template-release/README.md` —
  подготовка, проверка и публикация релиза.
